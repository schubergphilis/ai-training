In this lesson we look at the moment between two phases of work, such as
the end of planning and the start of implementation. A planning session
fills its context window with the files it read and the ideas it tried,
including the ones you turned down. When the plan is written, you choose
what the next phase starts with: the same session, a new session that
starts from the written plan, or a summary of the old one. Each choice
keeps different things, and each costs something different. The page has
no code to run.

The lesson builds on two earlier ones.
[*Telling the agent where the task is and where it stops*](/coding-with-agents/scoping-and-referencing/#point-at-the-file-instead-of-describing-it)
showed how to point an agent at a file by path, and a plan file is the file
you point the next phase at.
[*Directing the summary before compaction*](/customizing-agents/compaction/#what-the-summary-replaces-and-what-comes-back)
listed what Claude Code puts back after a compaction. This page uses that
list to compare the options. Where it names a Claude Code feature it says
so, and the vendor pages were checked on the date at the end of the lesson.

## What a session holds before you type

A new session doesn't start empty. Its **starting context** is everything
in the context window before your first message. In Claude Code that's the
system prompt, the `CLAUDE.md` or `AGENTS.md` instructions, the auto-memory
notes, the names of the tools from connected Model Context Protocol (MCP)
servers and a one-line description of each skill (@Claude Code context window).
Other agents load their own set, and most load an instructions file.

The starting context stays in the window for the whole session. Claude
Code sends the whole conversation with each request it makes
(@Claude Code costs), and the starting context goes with it. A large starting context takes room
from the task in every session, including the short ones. In Claude Code
the `/context` command shows what fills the window, by category
(@Claude Code context window).

You make it smaller in two ways that the costs page names
(@Claude Code costs). Move instructions for one workflow, such as how to run
a database migration, out of `CLAUDE.md` and into a skill, which loads its
full text only when it is used. And run `/mcp` to turn off the servers you
don't use. The lesson [*Writing project instructions the agent reads every session*](/coding-with-agents/project-instructions/)
gave a second reason to keep the instructions file short: the agent follows
a short file more reliably than a long one.

## Three ways to start the next phase

Take a planning session on the to-do program from earlier lessons. You asked
the agent for a `due <n> <date>` command. It read `todo.py`, `store.py` and
the tests, and tried two date formats. You turned down free-text dates,
because the list must sort by date. In the chat you also reminded the
agent not to edit `legacy/`. The agent wrote the plan to `PLAN.md`:
five steps, the files to change and the test to write first. The plan is
done, and implementation comes next. Here is what each option starts it
with.

**Continue in the same session.** The next phase has everything: each file
the agent read, each command output and each idea you turned down, word for
word. That history is also the problem. As the context window fills, the
agent follows earlier instructions less well and makes more mistakes
(@Claude Code best practices). Every request in the implementation phase
also sends the whole planning conversation again (@Claude Code costs).

**Clear, and start from the written plan.** In Claude Code, `/clear` starts
a new session (@Claude Code costs). The next phase has the starting context,
the repository with its uncommitted changes and the files you point it at,
and nothing from the conversation. For a spec that is finished, the
best-practices page advises this: start a fresh session to carry it out, so
the context holds only the implementation and the spec is in a file you can
refer to (@Claude Code best practices). The costs page adds that `/clear`
costs nothing (@Claude Code costs). What you lose is anything that was said
and not written down.

**Compact, then continue.** `/compact` replaces the conversation with a
summary. After it, Claude Code reads the project-root `CLAUDE.md`, the
auto-memory notes and the plan from plan mode again from disk. It also
reads up to five of the files the agent read or edited, the most recently
modified first. What the commands printed and the steps the agent reasoned
through are not kept word for word (@Claude Code context window). The
context-window page suggests `/compact` with instructions before you start a
long new task, so the summary keeps what you name (@Claude Code context window).
A compaction of a long conversation is itself a large request, because the
agent reads all of it to write the summary (@Claude Code costs). And a
summary can drop a detail whose importance shows only later
(@Anthropic context engineering).

Two more options are variations on these. A handoff file is a written plan
for a session that is not done: what was done, what is left and what was
decided. And a subagent starts with a clean context of its own and reports
back a short summary, so a large search stays out of your window
(@Anthropic context engineering).

## Decide at the boundary

**Deciding at a phase boundary** is choosing what the next phase starts
with when one phase ends. The sources give no rule for it, but they point
at one question: does the next phase go on with the same problem, or
start a new one?

Implementation that follows a finished plan is a new problem. It needs the
plan, the files the plan names and the reasons behind the plan's choices.
It doesn't need the planning conversation, so clear, and start from the
plan file. A debugging session in the middle of one hard bug is the other
case. The best-practices page says that sometimes you should let the
context grow, because you are deep in one complex problem and the history
is worth keeping (@Claude Code best practices). Between the two, compaction
fits work that keeps going back and forth on one problem, and notes in a
file fit work with clear milestones (@Anthropic context engineering).

Whatever you choose, do one step first: write down what the next phase
must keep. Clearing drops the whole conversation, and compacting keeps only
what the summary states. In the planning session above, that is the reason
you turned down free-text dates. Add it to `PLAN.md` and read the file.
Then clear, and start the new session with a brief that points at it:

```text
Implement the due command as PLAN.md describes. Start with step 1, the test.
```

The rule about `legacy/` that you typed in the chat an hour ago needs no
line, because it is already in `AGENTS.md`, and the new session loads that
file. A rule that is only in the chat needs a line in a file, or it is gone.

<Pitfall title="The reason the summary dropped">
At the end of a long planning session, an engineer runs `/compact` and goes
on to implementation. The plan is in the summary, and the reason for
turning down free-text dates is not, because it was said once in the chat
an hour earlier. An hour later the agent proposes free-text dates "to keep
the change small", and the engineer explains the reason a second time. A
summary keeps what its writer judges important at that moment, and a
detail can turn out to matter later (@Anthropic context engineering). The
rule: before you clear or compact, put what the next phase must keep in a
file, and read the file.
</Pitfall>

<Recap>
1. The starting context is everything in the window before your first message, and it goes with each request, so keep what the task never needs out of it (@Claude Code context window) (@Claude Code costs).
2. At a phase boundary you choose what the next phase starts with. It can keep the whole history or a summary of it, or start again from what's in files.
3. Continuing keeps everything, and a full window makes the agent follow its instructions less well (@Claude Code best practices).
4. Clearing and starting from the written plan fits a phase that starts a new problem, such as implementation after planning (@Claude Code best practices).
5. Compacting keeps a summary and drops the detail, and it is itself a large request (@Claude Code costs).
6. Before you clear or compact, write what the next phase must keep in a file and read the file back.
</Recap>

<Habit id="plan-file-before-clear">
At the end of your next planning session, add the decisions from the chat to the plan file before you clear, and start implementation in a session that points at the file.
</Habit>
