A colleague asks for a change to the to-do program: "Done items clutter
the list. Can you tidy it? I still want to see what I finished last
month." The request sounds clear until you try to build it. Does "tidy"
mean the `clear` command the program already has, which deletes done
items? Or does it mean moving them somewhere they can still be read? In
this lesson the agent interviews you about the feature before any plan
exists. You answer its questions, and together you settle on the words
for the design. At the end you check two files against those words: the
spec, and the plan that a fresh session writes from it.

*Deciding whether to build it at all* ended with success criteria a
stranger could check. You can only write those once you know what the
feature is. For a larger feature, the Claude Code best
practices page recommends that the agent interviews you first and writes
a spec, and that a new session then works from that spec (@Claude Code best practices).
The agent's questions bring out the decisions you haven't made yet, at a
point where a change to them is still cheap.

## The fixture

The fixture is the to-do program from *Your first session with a coding
agent*, some weeks later. It has a `clear` command and is split into three
modules. It is in the course repository under
`site/examples/coding-with-agents/agent-interviews-you/`. Copy that whole
directory to a place of its own. The copy holds `fixture-repo/`, where the
agent works, a script `check_terms.py` and a `sample/` directory that the
second half of the lesson uses. The reset is to delete the copy and copy
again. Working in a copy also keeps the course's own instruction files out
of the session, because Claude Code, for example, loads the instruction
files in every directory above the one it starts in (@Claude Code memory).

Claude Code's auto memory is on by default in local sessions. It saves
notes that the agent writes for itself and loads them into the next session
of the same project. It files the notes under the git repository, or
under the project root outside one (@Claude Code memory). In this lesson a
note from the interview would reach the fresh session that is meant to
start without it, and a reset copy at the same path would load the notes
again. So start every Claude Code session in this lesson with auto memory
turned off. Change into `fixture-repo` first, because this command starts
the agent in the directory you run it from:

```sh
CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 claude
```

With another agent, check whether it keeps notes between sessions, and
turn that off for this lesson. Before you start the agent, look at the
list from `fixture-repo`.

## Asking for the interview

A design interview is a session where the agent asks and you answer. It
comes before the agent plans anything or writes any code. Start your coding
agent in `fixture-repo`, with auto memory off as above, and give it a short description of the feature with the request to
interview you. Ask for questions about behavior, edge cases, risks and
trade-offs, and tell it to skip what it can read in the code. Tell it when
to stop, and what to write when it does.

```text
I want a way to tidy the to-do list. Done items clutter it, but I still
need to see what I finished last month. Before you plan anything or
change any code, interview me about this feature. Ask one question at a
time. Ask about how it should behave, the edge cases, what could go
wrong, and the trade-offs, and don't ask what you can find out from the
code. When a word could mean two different things, ask me which one I
mean. Keep going until nothing is open. Then write TERMS.md, one line per
term in the form "- **term**: meaning. Avoid: word, word.", and SPEC.md,
which uses only those terms. Put what I left undecided under
"Open questions" in SPEC.md.
```

In Claude Code, the best practices page suggests naming its
`AskUserQuestion` tool in the request (@Claude Code best practices). The
agent then asks its questions through that tool. Another agent asks its
questions in the chat.

The exchange below is illustrative. It was written for this lesson and
not recorded from a model. It shows the kind of first question that the
request should produce.

The agent's first question found the word that could mean two things. Your
answer chose one meaning and gave the new thing a name. The second question is a
decision you might not have made before the interview. Answer each question
with a decision. When you have none, say "not decided yet". The agent then
lists the point under the open questions.

<Pitfall title="An answer to get to the code">
In one interview the agent asked whether archived items should record the
date they were archived. The engineer wanted to get to the code and typed
"yes, add the date". The spec now had a date field with its own format and
time zone, and the fresh session built them. The `archive list`
output grew a column that nobody had asked for, and the diff was twice the
size it needed to be. The rule: an answer you make up to move on becomes a
requirement the agent builds. Say "not decided yet", and the spec lists the
point as open.
</Pitfall>

## Writing down the terms

During an interview the words drift. You say "done" and the agent says
"completed". A sentence later the spec says "finished". Each word
seems clear to whoever uses it. A fresh session that reads the spec sees
three words and has to guess whether they name one thing or three, and
some of its guesses are wrong.

The fix is a shared vocabulary: one agreed meaning for each term of the
feature, written down, and used the same way in the conversation, the spec,
the plan, and the code. The idea comes from domain-driven design, a way of
building software that Eric Evans described (@Evans 2003). His free reference
summary says to use one language in speech, writing and code, and to treat
a change in that language as a change to the design (@Evans DDD Reference).
This lesson takes only that part: a short list of terms, in plain words,
each with the words to avoid.

The `sample/` directory in your copy holds the files an interview about the
archive feature could end with. This is `sample/TERMS.md`:

```md
# Terms

- **item**: one line of the to-do list, with its text and its done mark. Avoid: task, tasks, entry, entries.
- **done item**: an item marked with `done`. Avoid: completed, finished.
- **archive**: move every done item from the list to `archive.json`, where `archive list` shows it. Avoid: hide, hides, hidden.
- **clear**: delete every done item from the list for good. It never touches `archive.json`. Avoid: purge, wipe.
```

The avoid words are the ones that came up in the interview for the same
thing, or for a different thing that is easy to confuse with it. "Hide"
is on the list because a hidden item is still in `todos.json`, and an
archived one is not.

## Checking the spec against the terms

that uses an avoided word. It matches whole words and ignores case. Leave
the interview session running in its own terminal, and open a second
terminal for the script. Change into the top of your copy there and run
the script on the sample spec.

## Planning from the spec in a fresh session

The best practices page suggests that a new session carries out the
spec, because its context then holds the work and nothing of the long
interview (@Claude Code best practices). Write the plan in a new session
too. End the interview session, start a new one in `fixture-repo` with
auto memory still off, and ask for a plan that uses the term list.

```text
Read TERMS.md and SPEC.md. Write PLAN.md with the steps to build what
SPEC.md describes, using the terms in TERMS.md and no other words for
them. Don't change any code yet.
```

When the plan is written, run the check on it in the second terminal, from
the top of your copy:

```sh
python3 check_terms.py fixture-repo/TERMS.md fixture-repo/PLAN.md
```

An avoided word in the plan means one of two things. Either the plan
slipped and you correct the word, or the spec left something open that the
plan filled in with a guess. In the second case, the fix belongs in the
spec first.

<Recap>
1. For a larger feature, ask the agent to interview you before it plans, and to write a spec when nothing is open (@Claude Code best practices).
2. Answer each question with a decision, or with "not decided yet". An answer made up to move on becomes a requirement.
3. Write the terms the interview settled into a short list, each with its meaning and the words to avoid, and use the same words in the spec, the plan and the code (@Evans DDD Reference).
4. Check the spec and the plan against the term list. A drifted word is either a slip or a decision written down wrong, so read the whole line.
5. Start the plan in a fresh session that works from the spec and the term list, without the interview in its context.
</Recap>

<Habit id="ask-for-the-interview">
The next time you hand an agent a feature that takes more than one sentence to describe, ask it to interview you before it writes a plan.
</Habit>
