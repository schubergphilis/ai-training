*Splitting the work into components the agent can build one at a time*
wrote the acceptance test for the import parser, and that test treats a
line that starts with `x ` as a done item. The rule came from the
colleague who asked for the feature. They remember their old app writing
`x `, and nobody has looked at the file. In this lesson we check that
rule before the parser is built. We write down the one question, have
the agent build the smallest program that answers it, put the answer in
the spec and delete the program.

*Let the agent interview you* ended with open questions in the spec, and
some of them can't be settled by talking. Whether a file uses one done
mark or two is a fact about the file, and a short program finds it out
faster than a meeting does. Thomas and Hunt call this a prototype built
to learn: it answers a question, it can leave out completeness and
robustness, and it is thrown away when the question is answered
(@Thomas 2019). With a coding agent, such a program takes a minute to
write, so trying the idea often costs less than discussing it.

## The fixture

The fixture is in the course repository under
`site/examples/coding-with-agents/prototype-to-throw-away/`. Copy that
whole directory to a place of its own and change into the copy. It holds
`SPEC.md`, the spec for the `import` command of the to-do program, and
`old-list.txt`, a copy of the colleague's old file. A `sample/` directory
holds a script that the second half of the lesson uses. The other files
are for the course's own checks. The reset is to delete the copy and copy
again.

The spec ends with this section:

```md
## Open questions

- Which done marks the old file uses. The colleague thinks it is `x` and a
  space, but nobody has looked. `old-list.txt` is a copy of the file.
```

If the answer is "only `x `", the parser and its test don't need a
change. A second mark in the file would make the parser import those
items as open. The test would still pass, because none of its input lines
has that mark.

## One question before any code

A throwaway prototype is a small program built only to answer one design
question, and deleted once it has. The question comes first, written in
one sentence, before you ask for any code. Without it, the agent builds
whatever seems useful: a parser, then a test for the parser, then a
command that calls it. That's a first version of the import, built
without the components and checks that *Splitting the work into
components the agent can build one at a time* designed.

A prototype can answer a question when the program prints the answer,
such as a count or two outputs side by side.
"Which done marks does `old-list.txt` use?" is such a question. "Should
we build the import at all?" isn't, because no program prints the answer.
"How should the import work?" isn't either, because it asks for the whole
design.

## The smallest program that answers it

Start your coding agent in the copy and give it the question, and say
what the program reads and prints. Say what to leave out, too. Tests,
error handling and structure are effort spent on code that you delete,
and a brief that doesn't mention them leaves that choice to the agent.
Say also that it may create one file and change nothing else.

```text
Read SPEC.md. Its open question is which done marks old-list.txt uses.
Write a throwaway script, count_forms.py, that answers only that. It reads
old-list.txt (hard-code the name), counts the blank lines, and prints how
many lines start with each first word, most common first, the top five.
No tests, no error handling, no command-line options. Create only
count_forms.py, and don't start on the import.
```

Counting first words is enough. A done mark is the first word of its
line, and a mark that the colleague forgot shows up near the top of the
list. The course ships one version of such a script in
`sample/count_forms.py`, so the output below is checked on every build:

```python
# Throwaway: answers which done marks old-list.txt uses. Delete after.
from collections import Counter
from pathlib import Path

lines = Path("old-list.txt").read_text(encoding="utf-8").splitlines()
blank = sum(1 for line in lines if not line.strip())
words = Counter(line.split()[0] for line in lines if line.strip())
print(f"{len(lines)} lines, {blank} blank")
for word, count in words.most_common(5):
    print(f"{word}: {count}")
```

The file name is hard-coded, and the whole file is read at once. It has
no functions, tests, or checks. In the parser each of those would be a
defect, and for one run on a file of 37 lines none of them matters.

## Write the answer down, then delete the program

The output answers the question. The file has two done marks: `x`
starts ten lines and `[x]` starts four. A parser built from the spec as
it stands would import four done items as open. The prototype found the
fact, and the decision is still yours. Here the decision is that `[x] `
marks a done item too. Write it into the behavior and take the question
out of the open questions:

```md
2. A line that starts with `x` or `[x]` and a space is a done item, and
   the mark isn't part of its text. The old file uses both (10 and 4
   lines).
```

The acceptance test from *Splitting the work into components the agent
can build one at a time* gets one more input line, such as
`"[x] Pay the bill"`, so that it fails on a parser that knows only `x `.
Then delete both scripts:

```sh
rm count_forms.py sample/count_forms.py
```

The answer is in the spec, where a fresh session and a reviewer read it.
The code that found the answer is gone, so nobody can build on it. In
an interview with Venners, Hunt and Thomas compare a prototype to the
front of a film set, with no building behind it. They say it is made to
be thrown away, and that the code a system keeps is a different kind,
which they call tracer code (@Artima tracer bullets).

<Pitfall title="The prototype that became the parser">
An engineer had an agent write a quick script to see how an old file
marked its done items. The script worked, so the engineer asked the agent
to add the import command around it. The script read the whole file into
memory, had a hard-coded path and no tests, and it was now the parser. A
month later a colleague imported a much larger file, and the import
stopped with an error about a path that existed only on the engineer's
laptop. The rule: a prototype answers its question and is deleted, and
the parser is built from the spec, with its own test.
</Pitfall>

## Small on purpose

In 1975, Fred Brooks advised teams to plan to throw away the first
version of a whole system, because they would anyway. In the 1995
anniversary edition he took that advice back. He wrote that it assumed a
system is designed, built and tested in one pass, and that he now
preferred to grow a system step by step (@Brooks 1995). A throwaway
prototype in this lesson is a different thing from a first version of
the system. It is a few lines that answer one question that you wrote
down before it existed. The system itself grows one checked component at
a time, as *Splitting the work into components the agent can build one
at a time* planned it.

<Recap>
1. A throwaway prototype is a small program built to answer one design question, and it is deleted once it has (@Thomas 2019).
2. Write the question down in one sentence before you ask for code. A program that answers no named question grows into a first version of the system.
3. Brief the agent to leave out tests, error handling and structure, and to create one file. They are effort spent on code that you delete.
4. Write the answer and your decision into the spec, and update the test, before the program is deleted. A fresh session reads the spec, not the chat.
5. Keep the prototype small. Brooks later took back his advice to throw away a whole first version (@Brooks 1995), and the system grows one checked component at a time.
</Recap>

<Habit id="name-the-question-first">
The next time you are about to argue about a design point with a colleague, ask whether a short program could settle it, and write the question down before anyone writes the program.
</Habit>
