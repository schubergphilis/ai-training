A coding agent writes tests quickly, and they pass. That tells you the
tests agree with the code, and it doesn't tell you they would notice if
the code were wrong. In this lesson you break a small program on
purpose and run the tests an agent wrote for it. Some of them still
pass, and you rewrite one of them so it checks what the program must do.
You see why a test that uses only the small interface of a module keeps
working when an agent changes the inside. Then you review a change the agent made to the same program, and find
the docs it left out of date.

The program is `shop/`, a pricing module for a small web shop, in the
course repository. It adds up the lines of an order and adds shipping:
4.95 euros (EUR), or nothing for an order of 50.00 EUR or more.

```python
FREE_SHIPPING_FROM = 50.00
SHIPPING = 4.95


def shipping(amount):
    """Return the shipping cost for an order with this subtotal."""
    if amount >= FREE_SHIPPING_FROM:
        return 0.0
    return SHIPPING
```

## Break the code on purpose

**Testing** with an agent means keeping tests that prove what the code
does for its users, and reviewing the tests the agent writes as closely
as the code. Agents produce tests readily, and some of those tests can
pass because they repeat what the code happens to do. The Academy course
The AI-native SDLC playbook (SDLC is short for the development life
cycle of software) argues that when an agent produces most of a team's
code, review and testing become the slow steps (@Academy ai-native-sdlc-playbook).
A quick way to review a test is to make the code wrong and see whether
the test notices.

From the root of your clone of the course repository, copy the shop to a
place of your own, and run its tests there.

```sh

python3 test_pricing.py; echo "exit status $?"
```

<Pitfall title="The test that learned the new answer">
An engineer asked an agent to add discount codes to a checkout. After
the change, a test that checked the total of a known order failed by
one cent, because the new code rounded twice. The agent changed the
assertion to compare the totals to one decimal place, and the suite
went green while every order with a discount showed a total one cent
off. A new expected value in a test is a change to what the program
promises. Review it like a change to the spec, and reject one the brief
didn't ask for.
</Pitfall>

## Keep the tests fast and unchanged

An agent reruns the tests after every change. How long they take
decides how many attempts fit in a loop: a one-second suite can run
after each edit, and a twenty-minute suite gets run once at the end, or
skipped. The example instructions file in the vendor guide for Claude
Code has a line for this. It asks the agent to prefer running single
tests to the whole suite, for speed (@Claude Code best practices).
Give the agent the fast tests for the part it changes, and run the full
suite before the merge.

The agent also must not change the tests to get a pass. The shortest
way to make a failing change pass is to delete the test, skip it or
loosen its assertion, as the agent in the pitfall did. When an agent
may edit the tests, the blast radius of one wrong change includes the
check that should catch it. So the rule for an agent is that it never
deletes or weakens a test. A test it thinks is wrong makes it stop and
explain why, and the decision is yours.

A rule in the project instructions is a request. Claude Code reads its
instructions file when a session starts and uses it as context, and
nothing in the file is enforced (@Claude Code memory). The
rule makes a weakened test less likely, and the review of the test
files is what finds one.

## Test through a small interface

**Deep modules** do a lot behind a small interface. John Ousterhout
describes the interface of a module as what its callers have to learn,
and the code behind it as what they get in return. He argues that a
good module gives its callers a lot for a little (@Ousterhout 2021). A
shallow module has an interface nearly as large as its code, so its
callers have to know how it works inside.

The shop's interface for a price is `total(lines)`. A caller passes the
lines of an order and gets the amount to pay. It doesn't need to know
the threshold, the shipping price or where the rounding happens. The
rewrite of `test_total_adds_shipping` that catches a wrong price uses
only that interface:

```python
assert total([(1, 30.00)]) == 34.95
```

It fails when the price is wrong, and it keeps passing when an agent
changes the inside of `pricing.py` correctly, for example by storing the
prices in cents. Both tests that mirrored the code reached past `total`:
one compared with `SHIPPING`, and the other called the helper functions
that `total` calls. A test that depends on the inside of a module has
to change when the inside changes, and it can agree with a wrong value
there.

A deep module also helps the next session. An agent that changes the
shipping rule edits `pricing.py` and its tests and no other code,
because no caller knows the rule. The next section shows that the
documentation still needs the same change. An agent that only calls the
module needs to read the interface. Ousterhout calls it information
leakage when one design decision, such as the shipping price, is known
in several modules (@Ousterhout 2021). An agent can leak a decision in a change
that passes every test, so review the interface in a diff as closely as
the code. When a function gets new parameters, ask what each caller now
has to know.

## Documentation is part of the change

**Documentation** is the written explanation of how a system behaves:
the README, the pages in `docs/`, and the comments and docstrings in
the code. An agent can write good documentation from code, and it can
just as easily change the code and leave the documentation saying
something else. Treat the docs as part of the change. The brief names
what to update, the project instructions say where the docs are, and the
review checks them.

The instructions file of the shop, `AGENTS.md`, says where its docs are.
The Claude Code guide suggests that an instructions file links to
detailed documentation and doesn't copy it in (@Claude Code best practices).

```text
- Run `python3 test_pricing.py` after every change, and read what it prints.
- Never delete a test or loosen an assertion to make a change pass. If a
  test looks wrong, stop and say why.
- Documentation is in three places: `README.md` for customers,
  `docs/pricing.md` for the full rules, and the docstrings in `pricing.py`.
  A change to a price or a threshold updates all three in the same change.
```

<Exercise stretch="Then pick one test an agent wrote in your own project, break the line of code it is about on purpose, and see whether the test fails.">
The exercise takes about ten minutes and gives you one rewritten test
and a short list of stale lines. It practices the checks that find a
test that can't fail and documentation that no longer matches the code.

From the root of your clone, make a fresh copy of the shop for the
first part:

```sh
cp -R site/examples/coding-with-agents/tests-and-docs-that-hold/shop ~/shop-boundary
cd ~/shop-boundary
```

In `shipping`, change `>=` to `>`. Before you run the tests, write down
which of the five you expect to fail. Run `python3 test_pricing.py` and
compare. For every test that passes, name one bug in `pricing.py` it
would not catch. Then rewrite `test_large_order_ships_free` so that it
fails with the break in place and passes without it.

For the documentation, go back to the root of your clone, make one more
fresh copy and give it a tagged commit:

```sh
cp -R site/examples/coding-with-agents/tests-and-docs-that-hold/shop ~/shop-docs
cd ~/shop-docs
git init
git add .
git commit -m "Before the agent's change"
git tag before-change
```

Start your own coding agent inside `~/shop-docs`, so it works on the
copy and not on your clone, and give it the brief from this lesson.
When it is done, run these commands:

```sh
git add -A
git diff --cached --stat before-change
python3 test_pricing.py
grep -n "50.00" README.md docs/pricing.md pricing.py
```

A good result has a list of expected failures that matches the run, a
rewritten test that fails with the break and passes without it, and a
review that names every place `AGENTS.md` lists that still gives the old
threshold, or confirms that none does. Then answer one question: which
test in your own project would you break first, and why that one?
</Exercise>

<Recap>
1. Review an agent's test by making the code wrong on purpose and running it. A test that still passes either gives the code an input that never reaches the broken line, or takes its expected value from the code it tests, so it mirrors the implementation. Rewrite it with an input that reaches the line and the value the program must produce, from the spec or worked out by hand.
2. Give the agent the fast tests for the part it changes to run in its loop (@Claude Code best practices), and run the full suite before the merge. The agent never deletes, skips or loosens a test to make a change pass. When a test looks wrong, it stops and says why.
3. A rule in the instructions file is context for the agent, and nothing enforces it (@Claude Code memory). Read the diff of the test files to confirm that no test was deleted, skipped or loosened.
4. Deep modules do a lot behind a small interface (@Ousterhout 2021). Test them through that interface, and review an agent's diff for a change that makes callers know what the module used to hide.
5. Documentation is part of the change. The brief names what to update, the instructions say where the docs are, and the review searches those places for what the change made stale.
</Recap>

<Habit id="break-one-line-first">
The next time an agent's change comes with new tests, change one line of its code to make it wrong, run the tests, and see which of them notice before you approve.
</Habit>
