In the previous lesson you reviewed the due-dates branch yourself, and you
found five problems behind a summary that called the work done. In this
lesson a second agent session reviews the same branch. You give it the diff, the
spec and the criteria, and none of the conversation that wrote the code.
Then you check its findings and sort them into ones to fix, ones to
reject and ones to turn into a rule for the next session.

A review from a model doesn't replace yours. It is fast, and it reads
every line of the diff. It can also be wrong, and it can find problems
that aren't there. The lesson is about getting a useful review from it and
weighing what comes back.

## Why the session that wrote it is the wrong reviewer

The session that wrote a change holds the reasoning behind every line. Ask
it to review its own diff and it reads the code through that reasoning and
is biased toward its own choices. Claude Code's guide to good practice
makes the same point. It suggests a second session for the review, because
the model in the first one leans toward the code it produced there
(@Claude Code best practices).

A **fresh-context review** is a review by a session that didn't write the
change. It receives the diff, the specification and the criteria to check.
The steps that led to the code stay out of its context. Its verdict then
rests on what the change does, measured against the spec
(@Claude Code best practices). In Claude Code you can open a new session
in a second terminal, or run `/clear` to empty the current one before the
review (@Claude Code best practices). You can also ask the writing session
to start a subagent for the review. An ordinary subagent starts in a
context of its own and reports back, but it gets its task from the writing
session (@Claude Code subagents). Tell the writing session to give it the
diff, the spec and the criteria. Its own account of the work stays out.
A fork is different: it is a subagent that starts with the whole conversation so far,
and a fork isn't a fresh reviewer (@Claude Code subagents). A bundled
`/code-review` skill gives the current diff to a new subagent that looks
for bugs. It doesn't know your spec. A review against the spec needs a
brief that you write (@Claude Code best practices).

## What the reviewer gets

The reviewer knows only what you give it. Point it at the change and at
the spec, and define a finding for it: a line of the spec that the change
breaks, or a change that no line of the spec asks for
(@Claude Code best practices). A reviewer looks for what you ask it to look
for. Ask for every possible improvement and you get a long list, whether
the code is good or not, and each item you act on makes the change larger
than the task. Keep the request to problems that make the program wrong or
miss the spec. Anything else the reviewer says is a remark you may ignore
(@Claude Code best practices).

For the due-dates branch, the brief is this. It points at `SPEC.md` rather
than restating it. The reviewer then reads the same text the agent worked
from. The transcript in this lesson is illustrative and doesn't record a
specific model's words.

## Check each finding before you act on it

A finding is a claim, and the reviewer is a model, so it can be wrong.
Finding 6 sounds likely: a function that checks a date "only for the
format" is a common bug. Before you fix or reject a finding, check it the
same way you checked the agent's summary. Most of these findings say what
a command does, so you can run the command.

## Fix, reject, or turn into a rule

- **Fix it in this change.** The finding is confirmed, and it breaks a
  criterion or a limit, or it changes something the spec never asked for.
- **Reject it.** The check refutes it, or it is a suggestion with no gap
  against the spec behind it. Write down why, in one line, so the next
  reviewer doesn't raise it again.
- **Fix it, and add a line to the project instructions.** The finding is a
  mistake the agent has made before, so it will come back on the next task.
  The lesson on [project instructions](/coding-with-agents/project-instructions/#fix-it-once-in-the-file)
  gives the same trigger for a new line in `AGENTS.md`.

Suppose this is the second branch this month where an agent deleted a
failing test to make the suite pass, and the first time an agent has
reformatted a file outside its task. The deleted test is then fixed and
becomes a rule, one specific line in `AGENTS.md`:

```md
- Never delete or weaken a test to make the suite pass. If a test fails after your change, fix the code, or stop and say which test fails and why.
```

<Pitfall title="The branch that grew after the review">
A developer asks a reviewer session for every gap it can find in a small
change to a payment form. It reports fourteen. The developer has the
writing session fix all of them, and the change comes back four times its
size. It now has a new validation module and twenty more tests, and
several of the tests pass the form input it can never receive. The next reviewer can't see the original fix inside it.
Two of the fourteen findings were real. Ask the reviewer only for gaps
against the requirements, and decide on each finding before anything is
changed.
</Pitfall>

## The review advises, and the gates decide

A review from a model is one more judgment about the change, next to
yours. It can be wrong, and the next model can be wrong in the same way.
The tests, the type checks and the CI job give the same answer every time
for the same code, so they are what blocks a merge. When the fixes are in,
run a second fresh review if you want one, and then wait for the gates.

<Exercise stretch="Then give the confirmed findings to a writing session, as one brief, and have a second fresh session review its fix with the same brief. Count what the second review finds.">
Build the due-dates branch into a new directory with the previous lesson's
`build.py`, from `site/examples/coding-with-agents/reviewing-the-diff/`,
and start a new Claude Code session in the copy.

```sh
python3 build.py ~/fresh-review
cd ~/fresh-review/fixture-repo
CLAUDE_CODE_DISABLE_AUTO_MEMORY=1 claude --permission-mode default
```

The environment variable turns auto-memory off, so the session loads no
note from an earlier session and saves none of its own
(@Claude Code memory). Manual mode, which the flag selects, lets the agent
read files without a prompt (@Claude Code permission modes). It asks you
before each edit, and before each command outside a short built-in list
of read-only ones. `git diff` is on that list and runs without a prompt
(@Claude Code permissions). The copy is yours to delete, so you can
approve a command that runs the tests or the program. An approved run of
the program can save the list into the copy, and `git status` then shows
the file as untracked. Refuse every edit, because this session reports and doesn't
fix. Type the brief from this lesson as your first message.

Sort what comes back into three lists: fix, reject, and fix with a rule.
Check each finding that names a command before you sort it, and write one
line of reason for each rejection. Write the rule line for `AGENTS.md`,
and don't commit it. Ten minutes is enough. Delete the directory when
you are done.

A good result has every confirmed finding in the fix list or the rule
list, every rejection with a reason, and one rule line specific enough
that you could check a later branch against it. Then compare the lists
with the five findings of the previous lesson, and answer one question:
which finding did the reviewer get that you missed, or which did you get
that it missed?
</Exercise>

<Recap>
1. A session that wrote a change is biased toward it. Give the review to a session that didn't write it, with the diff, the spec and the criteria, and none of the writer's reasoning (@Claude Code best practices).
2. Point the reviewer at the change and the spec, and define a finding as a line of the spec the change breaks or a change no line asks for. A reviewer finds what it is asked to find, and fixing every remark makes the change larger than the task (@Claude Code best practices).
3. A finding is a claim. Check each one before you act on it, then fix it, reject it with a reason, or fix it and add a line to the project instructions when the agent has made the mistake before.
4. The review is advice you weigh. The tests and the CI job decide whether the change merges.
</Recap>
