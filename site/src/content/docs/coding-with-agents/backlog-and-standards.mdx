In [the lesson on hooks and CI](/coding-with-agents/ci-and-hooks/) two
team rules moved out of a brief and into the project, where every session
runs them. The plan for the next change is often still in one person's
notes or in a chat thread, and the review comments that keep coming back
are in old pull requests. A new agent session starts without them. In this
lesson we move both to
a place the agent reads by itself: the spec into the team's issue tracker,
and a repeated review finding into a standards file or a check.

The project is the nightly sales import from the earlier lessons:
`importer.py` adds up the exports of one night and converts every amount
to euros with the rates in `rates.json`. The team wants to import a past
night again with the rates of that night, and has a short spec for it.

## Put the spec in the tracker

An agent-reachable backlog is the team's specs and tickets, kept in its
tracker, where people and agents can both read and update them. The tracker
also records which ticket blocks which. A spec in a private note helps one
person. The same spec as an issue helps every person on the team and every
agent session, because each of them can find it, read it in full, and
report on it there.

The spec for the past nights has two parts, and the second needs the
first. The importer has to keep the rates of each night before it can
import a past night with them. So the spec becomes two issues, each with
its own "done when" list, and a link between them. GitHub calls the link
"blocked by" on one issue and "blocking" on the other, and it marks a
blocked issue with an icon in the issue list and on project boards
(@GitHub docs creating-issue-dependencies). The order is then in the
tracker, where the next reader sees it, and not only in the head of the
person who wrote the spec.

With the GitHub command-line tool, `gh`, the two issues are two commands.
The bodies are the two files `issue-rates.md` and `issue-rerun.md` in
`site/examples/coding-with-agents/backlog-and-standards/` of the course
repository. `--blocked-by` takes the number of the issue that must be
done first (@GitHub docs creating-issue-dependencies). The second command
below assumes the first issue got number 1. Put the number of your first
issue in its place if it differs.

```sh
gh issue create --title "Keep the rates of each night" --body-file issue-rates.md
gh issue create --title "Import a past night with its own rates" --body-file issue-rerun.md --blocked-by 1
```

If `gh issue create --help` doesn't list `--blocked-by`, your `gh` is
older than the feature. Update it, or set the link on the issue page in
the browser, under **Relationships** in the sidebar.

In another tracker, look for the same two parts, perhaps under other
names: a ticket with a body, and a link type for "this one waits for that
one".
Use the link type. A person reads a sentence in the body such as "do this
after the rates one", but only a link lets the tracker mark the issue as
blocked.

## Let the agent read it from the command line

The agent reaches the tracker through the same command-line tool. The
vendor guide for Claude Code recommends command-line tools as the way to
work with outside services that costs the least context, names `gh` for
GitHub, and suggests that the agent read the `--help` of a tool it doesn't
know yet (@Claude Code best practices). These are the commands the agent
needs here:

```sh
gh issue list
gh issue view 2
gh issue view 2 --json blockedBy,blocking
```

`gh issue list` shows the open issues. `gh issue view` shows one issue in
full, and its output has a "Blocked by" row and a "Blocking" row when a
link is set. With `--json` and the fields `blockedBy` and `blocking`, the
same links come back as JSON (@GitHub docs creating-issue-dependencies).

The brief then names the tracker as the source of the work, and nobody
pastes the spec. The transcript below is illustrative and doesn't record a
specific model's words.

<Response>
The repository has two open issues. Issue 2, "Import a past night with its own
rates", is blocked by issue 1. Issue 1, "Keep the rates of each night",

"done when" list asks for `rates/2026-09-14.json` to be read for that

The commands run with the credentials you give the tool. If those are your
own login, the agent has your rights in every repository you can reach.
It can close issues and change labels there. Give the agent only the
rights it needs. Reading issues and adding comments is enough for most
work. If your tracker lets you make a token with fewer rights, use one for
the agent. In Claude Code you can also run the session in Manual mode.
Claude Code then asks you before most shell commands, and you read each
`gh` command before it runs. From version 2.1.283, a session started in a terminal starts in
auto mode by default, so you choose Manual mode on purpose with
`claude --permission-mode default` (@Claude Code permission modes).

## Write a repeated finding down once

Review comments have a second problem. A reviewer writes "use `Decimal` for
money, not `float`" on one pull request, and two weeks later writes the
same comment on the next one, for a change another session wrote. The
comment is in the old pull request, where no new session reads it. The
memory page for Claude Code names two moments to write a rule down that fit
here: the agent repeats a mistake, or a code review turns up a fact about
the project that the agent was missing (@Claude Code memory).

A standards file is the team's list of coding rules that no tool checks.
Human reviewers and agent reviewers read the same file, and check a change
against it. A short `STANDARDS.md` for the import could start like this:

```markdown
# Standards

Rules that no check enforces. Reviewers block a change that breaks one
of these, and mark every other style point as a suggestion.

## Errors

- An error message names the file it is about, and the row when there is one.
  For example: "nights/2026-09-15/store-03.csv, row 12: 5 fields, expected 4".
```

For an agent to read the file in every session, the project instructions
point at it. A line `@STANDARDS.md` in `CLAUDE.md` imports the file, and
Claude Code loads it at launch together with `CLAUDE.md` (@Claude Code memory).
A reviewer gets the same file through a link in the pull request template
or the review checklist.

Some findings don't need a line, because a script can find them. The
`float` comment is one. The [hooks and CI lesson](/coding-with-agents/ci-and-hooks/)
showed how a rule that must hold every time becomes a hook or a CI step,
and a repeated finding can take the same path. This check flags every call
to `float(` in the files it is given. It is crude on purpose. When the code
one day needs a float for something other than money, make the check
narrower then.

The check exits with status 1, so as a step in the CI job it fails the
pull request until the amount goes through `Decimal`. Once the check is in
CI, delete the `float` line from the standards file if you wrote one there.
The check runs on every change, and the file stays a short list of the
rules that only a reader can check. That length matters for the agent too:
the memory page advises keeping `CLAUDE.md` under 200 lines, and an
imported file loads at launch and takes context the same way
(@Claude Code memory).

## Block on the file, suggest the rest

The file also changes what a reviewer may block on. Google's code review
guide for reviewers says that on questions of style, the team's style
guide decides, and a style point the guide doesn't cover is the reviewer's
personal preference. It suggests a prefix such as "Nit:" for a small
improvement that the author doesn't have to make (@Google eng-practices). The guide
treats design as more than taste, and a bug or a design problem can still
block a change. For the
conventions of the code, the standards file is the team's style guide. A
broken rule from the file, or a failed check, blocks the change.
Every other style point is a suggestion.

That gives an agent reviewer a clear brief. Ask it to review the diff
against `STANDARDS.md` and to mark a style finding as blocking only when
it names the rule it breaks. Ask it to write every other style point as a
"Nit:", and to block on a bug as usual.
When a reviewer, human or agent, blocks on taste, the author can no longer
tell the rules in the file from the preferences, and starts to treat both
as optional.

<Pitfall title="The token that could do everything">
A team gave its agent the lead's own login for the tracker, because it was
already set up on the machine. One afternoon someone asked the agent to
"tidy up the backlog". It closed thirty issues it judged to be stale,
including four that waited on a decision from a customer, and nobody saw
it happen until the next planning meeting. The agent needed to read issues
and add comments, and the login could close and delete them. Give the
agent credentials for what the task needs, and read every command that
changes the tracker before it runs.
</Pitfall>

<Recap>
1. An agent-reachable backlog keeps specs and tickets in the team's tracker, where people and agents both read them. A spec in a private note or a chat reaches nobody else.
2. Record the order of the work with the tracker's own links. GitHub marks an issue that is blocked by another, and `gh issue view` shows the links (@GitHub docs creating-issue-dependencies).
3. The agent reads the tracker through a command-line tool, which costs little context (@Claude Code best practices). Give it the rights the task needs, and read each command that changes the tracker before it runs.
4. When a review finding comes back, write it in the standards file that human and agent reviewers both read, and import that file into the project instructions (@Claude Code memory). When a script can find the mistake, make it a check and delete the line.
5. Reviewers block on a rule in the file, a failed check or a real defect, and mark other style points as suggestions (@Google eng-practices).
</Recap>

<Habit id="second-time-write-it-down">
The next time you write a review comment you have written before, stop and add it to the standards file, or to a check, before you send the review.
</Habit>
