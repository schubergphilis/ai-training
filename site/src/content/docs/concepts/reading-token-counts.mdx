A colleague spends a morning in one chat with an assistant. She asks what a
kickoff email should contain, pastes her meeting notes, asks for a draft,
pastes a budget sheet, and at the end asks for a subject line. The last
question is one short line, and yet it cost about twice as much as the first one.
In this lesson we read the token counts of every request in that chat and
find out where the money went. Then we do the same for one prompt to an
agent. You install and run nothing: every count on the page is in a table.

The [lesson on what every token costs](/concepts/what-tokens-cost/#what-a-token-costs)
priced one call. The [lesson on one prompt and many
requests](/concepts/one-prompt-many-requests/#what-is-in-each-request)
showed that each request holds the whole history so far. This lesson puts
the two together.

## Two counts on every request

When software sends a request to a model, the reply comes back with a
short usage report, and that report holds two counts, the **input and output tokens** of the request
(@Claude docs messages). The vendor bills by these counts.

The input count is everything the request sent to the model. It's the
instructions, the tool descriptions if the assistant has tools, the history
of the conversation and the new message. The tool descriptions are input
tokens, and so are the tool results that come back (@Claude docs pricing).

The output count is everything the model wrote. That includes the visible
answer and a request for a tool. A model that thinks before it answers
writes its thinking as tokens too, and those are billed as output tokens
(@Claude Code costs). So the output count can be larger than the answer you
see. Both counts differ from the count of words on the screen, since the
vendor turns the request into its own format before the model reads it
(@Claude docs messages).

The two counts have different prices. On the vendor's price list an
output token costs five times as much as an input token, on every model
(@Claude docs pricing), and the example prices in the lesson on what every
token costs follow the same pattern. So the same total can mean two
different bills. Read the two counts apart, and price each one.

Some usage reports split the input count further: tokens written to a cache,
tokens read from it, and the rest. Together those parts are the whole input
(@Claude docs messages). The usage screen of one coding agent shows the
same split for a session (@Claude Code costs). The cache is the subject of
a later lesson in this course. In this lesson every request is billed at
the normal input price.

## A short chat, request by request

Here is the usage of the chat from the top of the page, one row per
request. The counts are round numbers written for this lesson, and the
prices are the example prices for a large model from the [lesson on what
every token costs](/concepts/what-tokens-cost/#what-a-token-costs): $6 per
million input tokens and $30 per million output tokens. The left column
says what was new in each request. The assistant's instructions are 500
tokens.

```text
chat session
request                                       input  output   input $  output $   total $
1. asks what a kickoff email holds              515     400   $0.0031   $0.0120   $0.0151
2. pastes meeting notes, asks for a draft     2,435     350   $0.0146   $0.0105   $0.0251
3. asks to make it shorter                    2,795     200   $0.0168   $0.0060   $0.0228
4. pastes a budget sheet, asks to add it      5,015     250   $0.0301   $0.0075   $0.0376
5. asks for a subject line                    5,277      15   $0.0317   $0.0004   $0.0321
total                                        16,037   1,215   $0.0962   $0.0365   $0.1327
```

Read the table one column at a time. The output column goes up and down
with the length of each answer. The input column only goes up. Request 1
sent the instructions and one question. Request 2 sent those again, plus
the first answer, plus the pasted notes. Each request after that held
everything before it, because the model keeps nothing between requests and
the earlier messages are passed in again with each new one
(@Claude docs messages).
This is **growing session cost**: every request in a conversation costs at
least as much input as the one before it.

Now compare the first and the last row. Both questions are one short line.
In request 1, most of the cost is output: 400 tokens of answer at the higher
price. In request 5 the answer is 15 tokens, and almost all of the cost is
input, the 5,277 tokens of conversation the subject line was sent with.
The two pasted documents are in that input, and they were paid for again in
every request after they arrived.

The row below is the same subject-line question asked
alone in a new chat, with only the instructions in front of it. A subject
line written that way knows nothing about the email, so this row is for the
price only.

```text
question 5 alone, in a new chat                 512      15   $0.0031   $0.0004   $0.0035
```

## One prompt to an agent

A chat sends one request for each message you type, and an agent sends one
for each step of its loop. One coding agent's cost guide explains that
the agent calls the model again whenever tool results are ready, and that
each of those calls holds the whole conversation so far (@Claude Code costs). So one
prompt to an agent can fill several rows of a usage report.

Here is the toy run from the [lesson on one prompt and many
requests](/concepts/one-prompt-many-requests/#what-is-in-each-request): find
the meeting note that mentions the June delivery, with a tool that lists a
folder and a tool that reads a file. The agent's instructions and its tool
descriptions are 1,400 tokens together. The counts are again written for
this lesson.

```text
one prompt to an agent
request                                       input  output   input $  output $   total $
1. the prompt                                 1,430      40   $0.0086   $0.0012   $0.0098
2. result: 3 file names                       1,530      40   $0.0092   $0.0012   $0.0104
3. result: the text of one note               3,970     120   $0.0238   $0.0036   $0.0274
total                                         6,930     200   $0.0416   $0.0060   $0.0476
```

The person typed one line, and the report has three rows. The first two
outputs are short, because a request for a tool is short. The input of
request 3 is more than twice that of request 2, because the full note came
back as a tool result and went into the history. Had the agent gone on to
a fourth step, the note would have been in that request too.

## Starting fresh

The history is what makes a late request expensive, so the cheapest way to
lower it is to drop it. When you move to a task that has nothing to do with
the conversation so far, start a new conversation. The old history adds to
the cost of every new request and gives the new task nothing it needs. The
vendor's cost advice for its coding agent gives the same rule for a switch
to unrelated work, because text from the old task is paid for again with
each new message (@Claude Code costs).

When you need to keep going on the same task, some tools can compact the
conversation: they ask the model to write a short version of the history
and continue from that. The requests after the summary are smaller. The
summary request itself is large, since the model reads the whole
conversation for it, and a fresh start with a new conversation is free
(@Claude Code costs).

<Pitfall title="Blaming the long answers">
A team's assistant costs more than they expected, and the first guess is that
its answers are too long. They add "keep answers short" to the instructions.
The bill barely moves. The usage report shows why: the output counts were a
few hundred tokens a request, and the input counts were tens of thousands,
because a reference document was attached to every conversation and the
conversations ran all day. The rule: read the input and the output counts
before you guess, and look at what the input holds before you shorten the
answers.
</Pitfall>

<Exercise stretch="If a tool you use shows a usage screen with input and output counts, open it after your next long session. Find the request with the largest input and say what was in its history.">

Here is the usage report of another chat, about planning a team day. The
counts are written for this lesson, at the same example prices. On paper or
in a note, write for each request its input and output count, and say in
one line what made the input grow. Then write two or three sentences on why
request 4, a one-line question, cost more than request 1, and what you
would do differently next time. Ten minutes is enough.

```text
exercise: chat about a team day
request                                       input  output   input $  output $   total $
1. asks for team day ideas                      520     600   $0.0031   $0.0180   $0.0211
2. pastes a price list, asks which fits       4,120     300   $0.0247   $0.0090   $0.0337
3. asks for the invitation                    4,435     250   $0.0266   $0.0075   $0.0341
4. asks if Friday is better                   4,693      60   $0.0282   $0.0018   $0.0300
total                                        13,768   1,210   $0.0826   $0.0363   $0.1189
```

A good result notes that the input grows on every row and the output does
not. It names the pasted price list as the jump in request 2 and says the
list was sent again with requests 3 and 4. It says that most of the cost of
request 1 is its long answer, and most of the cost of request 4 is the
history it was sent with. A good answer to the last part asks whether the
Friday question needed the price list at all. To close, ask yourself: in
your own last long chat, which pasted text did you pay for most often?

</Exercise>

<Recap>

1. Every request reports two counts. Input tokens are everything the
   request sent: instructions, tool descriptions, the history and the new
   message. Output tokens are everything the model wrote, thinking and tool
   requests included (@Claude docs messages).
2. An output token costs several times an input token, so read the two
   counts apart and price each one (@Claude docs pricing).
3. Each request in a conversation holds the whole history, so the input
   count only goes up. A short question late in a long chat can cost more
   than a long one at the start (@Claude Code costs).
4. An agent sends a request for every step of its loop, and every tool
   result goes into the input of the requests after it.
5. Start a new conversation for an unrelated task. Compacting makes later
   requests smaller, and the summary is one large request of its own.

</Recap>

<Habit id="new-task-new-chat">
The next time a chat with an assistant moves on to a task that has nothing to do with the conversation so far, open a new chat for it.
</Habit>
