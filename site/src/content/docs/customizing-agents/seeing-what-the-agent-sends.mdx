In this lesson we look at what Claude Code sends to the model, in three
places. The context meter shows how full the window is while you work.
The session record on disk holds every message, tool call and tool
result of a session. A request log, which you turn on for one session,
holds each request exactly as it was sent. The exercise connects one
more tool and follows it through all three.

The concepts course showed a toy harness's own log of
[what is in each request](/concepts/one-prompt-many-requests/#what-is-in-each-request):
the instructions, the tool descriptions and the history, sent again on
every call. The lesson on
[what the tool list costs](/customizing-agents/mcp-tool-cost/#what-the-tool-list-costs)
estimated what a server's tool definitions take from that request. Here
you look at the real requests of your own agent.

## Watch the context meter

In Claude Code, `/context` shows what fills the window right now, broken
down by category, with suggestions for what to trim (@Claude Code context window).
One of the categories is the tools of Model Context Protocol (MCP)
servers, shown as MCP tools. With tool search on, which is the
default, only the tool names are in the window, and the model loads a
full schema when a task needs it. With `ENABLE_TOOL_SEARCH=false` every
schema loads at the start (@Claude Code context window).

`/context` answers when you ask. A status line shows a number all the
time. Claude Code runs the status line command after each new reply from
the model, passes it the session data as JSON (JavaScript Object
Notation) on standard input, and shows what it prints
(@Claude Code statusline). The command runs on your machine and costs no
tokens. For this lesson the useful fields are these:

- `context_window.used_percentage`, the share of the window in use. It is
  counted from the input tokens of the last request, and it can be null
  early in a session.
- `context_window.total_input_tokens`, those input tokens, cache reads
  and cache writes included.
- `transcript_path`, the path of the session record on disk.

All three come from the statusline page (@Claude Code statusline).
`statusline.py` in `site/examples/customizing-agents/seeing-what-the-agent-sends/`
prints them on one line, and a dash for a field that is missing or null.
You point Claude Code at it with a `statusLine` entry in a settings file
(@Claude Code statusline):

```json
{
  "statusLine": {
    "type": "command",
    "command": "python3 /tmp/handbook-inspect/.claude/statusline.py"
  }
}
```

## Find the session in its record

Claude Code keeps data under `~/.claude` as you work. The transcript of a
session is `projects/<project>/<session>.jsonl`, and it holds every
message, every tool call and every tool result of that session
(@Claude Code claude directory). The project directory is named after the
project's path, with every character other than a letter or a digit
turned into a dash, so `/home/user/work/my-repo` becomes
`-home-user-work-my-repo`. On macOS a copy in `/tmp` is at
`/private/tmp`, and its directory starts with `-private-tmp-`.
The status line above gives you the file name, and `transcript_path`
gives the full path.

Resume and rewind read past sessions from these files, and they are the
place to look when a run went wrong yesterday and you want to see which
file the agent read before it did. They are also plain text and
unencrypted, so whoever can read your files can read them. A `.env`
file the agent opened, or a key that a command printed, ends up in the
record as well (@Claude Code claude directory). Claude Code deletes
records older than `cleanupPeriodDays`, which is 30 days unless you set
it. From version 2.1.288, `claude purge <path>` deletes a project's
transcripts, its memory and its lines in the prompt history, after it
shows you the plan (@Claude Code claude directory).

The record holds the session turn by turn. The system prompt and the
tool definitions that came with each request aren't in the page's list
of what it holds. For those you need the request itself.

## Log the requests on your machine

Claude Code can write every request it sends to a directory on your
machine. It is part of its OpenTelemetry monitoring, the standard it uses
to export usage data (@Claude Code monitoring). Telemetry is on only with
`CLAUDE_CODE_ENABLE_TELEMETRY=1`. `OTEL_LOG_RAW_API_BODIES=file:<dir>`
then writes the full body of each request to `<dir>/<uuid>.request.json`,
and from version 2.1.274 Claude Code adds one line per successful
response to `<dir>/index.jsonl`, with the session id, the `query_source`
that sent the request and the file names (@Claude Code monitoring).
`OTEL_METRICS_EXPORTER=none` and `OTEL_LOGS_EXPORTER=none` switch off both
exporters, so the events themselves don't go to a collector anywhere
(@Claude Code monitoring).
In our run in October 2026, the request files were written with both
exporters set to `none`. If your organization already collects Claude
Code telemetry, ask its administrators before you turn on the request
log, because their settings may send the events somewhere you don't
expect.

The monitoring page leaves request bodies out unless you ask for them.
The variable's description warns that a body carries the whole
conversation, so it reveals all that the switches for prompt text and
tool details would reveal (@Claude Code monitoring). A request file
holds the system prompt, every tool definition and every message so
far, with the full text of each file the agent read and any secret a
command printed. So keep the log on your own machine, in a directory
only your user can read and outside every repository. Turn it on for
the session you are investigating, and delete the directory when you
have your numbers. Don't send a request file to an online token counter
or paste it into a chat assistant.

Each request lists the tools in its `tools` field. In the Claude
application programming interface (API), a definition marked
`defer_loading` is sent to the API but stays out of the model's context
window until the model searches for that tool
(@Claude docs tool-search-tool). So `/context` shows what is in the
window, the request log shows what was sent, and the two can differ. In
our run on 7 October 2026, a `claude -p` run with tool search on and no
MCP server, the deferred tools were Claude Code's own built-in tools.
They appeared by name in a message, and the `tools` field held one
placeholder marked `defer_loading`. The exercise starts Claude Code
with `ENABLE_TOOL_SEARCH=false`, which loads every MCP tool definition
upfront (@Claude Code mcp), so each MCP tool definition in the log is
one the model reads.

A gateway can log requests too. You point `ANTHROPIC_BASE_URL` at it,
and the gateway can log every request that passes through
(@Claude Code llm gateway). Anthropic doesn't vouch for gateway products
made by others (@Claude Code llm gateway). A gateway you don't run
yourself also holds a copy of everything that passes through it, file
contents and secrets included. The log in a local directory never leaves
your machine.

Claude Code also sends requests of its own besides the turns of your
conversation, and the side requests are in the log too. The monitoring
page's cost counter sorts requests into main, subagent and auxiliary
ones. The `query_source` in `index.jsonl` is a different field, with
values such as `repl_main_thread` for the main conversation and
`compact` (@Claude Code monitoring).

`read_log.py` in the fixture directory reads a log directory and prints,
for each request, the estimated tokens of the system prompt, the tools
and the messages, at four characters per token. The `mcp tools` column
is the tool definitions of MCP servers and their share of the request.
Claude Code names an MCP tool `mcp__<server>__<tool>`
(@Claude Code permissions), and the script groups the tools by that
name. The `source` column is the `query_source` from `index.jsonl`. The
script skips a request without tools and leaves out a definition marked
`defer_loading`, and it prints how many of each it found.
`sample_log.py` writes a sample log of one side request without tools,
then one prompt that took three model calls, with three built-in tools
and a `notes` server with five tools, and runs `read_log.py` on it.

<Pitfall title="The log in the project">
A developer wants to measure their agent and points the request log at
`./request-log` inside the project, because that is where they work. At
the end of the day they run `git add .` and push. The forty request files
are now in the repository's history, with the full text of every file
the agent read that day, including the local `.env` file it opened to
check a port number. Deleting the files in the next commit doesn't remove
them from the history. The rule: a request log goes in a directory
outside every repository, readable only by you, and you delete it when
the measurement is done.
</Pitfall>

<Recap>
1. `/context` breaks down what fills the window by category, and a status
   line can show the share in use, the input tokens and the record's path
   after every reply (@Claude Code context window) (@Claude Code statusline).
2. The session record under `~/.claude/projects/` holds every message,
   tool call and tool result in plain text, secrets included, until
   `cleanupPeriodDays` or `claude purge` removes it
   (@Claude Code claude directory).
3. `OTEL_LOG_RAW_API_BODIES=file:<dir>` writes each request, with the
   system prompt, the tool definitions and the messages, to a local
   directory (@Claude Code monitoring). The log shows what each part
   costs in every request.
4. Turn the log on for one session, keep it in a directory outside every
   repository that only you can read, and delete it when you have your
   numbers. A gateway on `ANTHROPIC_BASE_URL` that you don't run holds a
   copy of the same data. Anthropic doesn't vouch for gateway products
   made by others (@Claude Code llm gateway).
</Recap>
