The last lesson wrote a short `AGENTS.md` for `invoice-mailer`, the
fictional Python service that renders invoices to PDF and sends them over
SMTP. A year later the same file has 57 lines. Each line was added for a
reason, and the agent now follows the file less well than it followed the
short version. In this lesson we make it short again with two moves. We
point at what only some tasks need, and we cut what no task needs.

The files for this lesson are in
`site/examples/customizing-agents/load-point-prune/` in the course
repository. `AGENTS.long.md` is the long file, `AGENTS.pruned.md` is one
pruned version of it, and `docs/` holds the files the pruned version points
at. The loading rules here are Claude Code's, checked against its
documentation on the date at the end of the lesson. Other agents load
their files in other ways, and the method transfers.

## Every loaded line is in every session

Claude Code reads its instruction files at the start of every session
(@Claude Code memory). Every line in them is in the context of every
task, the one-line typo fix as well as the release. The [lesson on what
tokens cost](/concepts/what-tokens-cost/#the-rule-that-got-buried) showed
what that does to a rule: it competes with all the other text in the
window, and a rule among many weighs less than a rule among few. The
vendor gives the same advice for instruction files in its own words. A
longer file takes more context, and the agent follows it less closely
(@Claude Code memory).

The choice for each piece of guidance is **loading versus pointing**.
Loading puts the text in the instruction file, so it is in context
whether the task needs it or not. Pointing puts one line in the file that
says where the text is and when to read it, and the agent opens the file
only when a task calls for it. Anthropic's engineering team describes the
same split for agents in general. An agent can keep a short reference such
as a file path and load what it points at with a tool at the moment it
needs it. Claude Code works this way: its instruction files go into
context at the start, and it finds the other files of the project with
search tools as it works (@Anthropic context engineering).

Load what nearly every task needs: the test command, the branch rule, the
mistake the agent keeps making. Point at the rest. The vendor's examples
of guidance to move out of the file are a procedure with many steps and a
rule that matters for only one part of the code. Claude Code also has two
places for those that load less often than the instruction file. A skill
loads when you call it or when the agent decides it fits the task, and a
rule file with a `paths` field loads only when the agent works with files
that match it (@Claude Code memory).

## An import still loads

Claude Code lets an instruction file import another file with a line such
as `@docs/release.md`. The import isn't a pointer. Claude Code expands
the imported file into the context at start-up, next to the file that
imports it, and the vendor says plainly that an import keeps a long file
tidy without making it cheaper (@Claude Code memory). A path in a code
span, such as `` `docs/release.md` ``, is plain text and doesn't import anything.
The agent reads that file only if it decides to open it.

`startup.py` in the lesson folder counts the lines each version of the
file puts in context at the start of a session. It follows the import rule
above, simplified. `AGENTS.pruned.md` points at two files with lines such
as "To cut a release, read `docs/release.md` and follow it step by step".
`AGENTS.imports.md` is the same file with each of those two lines replaced
by an import.

```sh
cd <course-repo>/site/examples/customizing-agents/load-point-prune
python3 startup.py
```

## A pointer says when

A pointer works only when the agent opens the file it names, and the agent
decides that from the pointer line alone. The vendor gives an example of
this case. A `CLAUDE.md` that tells Claude in a sentence to read
`AGENTS.md` gets `AGENTS.md` read only when Claude decides to open it
(@Claude Code memory). So write the pointer as a condition and a
place: "Before you change a file in `templates/`, read
`docs/templates.md`." The condition is what the agent matches against the
task. A bare "see `docs/`" gives it no task to match, and "always read
`docs/release.md` first" makes it read the file in every session, which
costs as much as loading it.

## Cut what does nothing

Pointing makes the file shorter. **Pruning instructions** makes it shorter
again, by deleting lines that no task needs. The vendor's test asks of
each line whether the agent would get something wrong without it, and a
line the agent wouldn't miss goes (@Claude Code best practices). The
lines that fail the test are usually one of these.

**A rule the agent follows anyway.** "Write clean, readable,
well-documented code" describes what the agent does without it, and so
does a line about a convention the agent already applies, such as type
hints in a code base that has them everywhere.

**A fact the code already states.** The formatter's configuration sets the
quote style and the line length, so "use double quotes" and "keep lines
under 100 characters" repeat it. The dependency list is in
`pyproject.toml`, and the paragraph about the modules repeats the folder
names. A copy of a fact can also go stale while the code changes, and then
the agent has two sources that disagree.

**A rule for a problem that has gone away.** "Keep the PDF library below
version 52" was right when the crash happened. The project has used
version 62 for a year, and the line now asks the agent to downgrade.

**A line that contradicts another.** The long file says `uv run pytest`
under Commands and `python -m pytest` under Rules. When two instructions
contradict each other, Claude may follow either one (@Claude Code memory).
Resolve a conflict by keeping one version, and keep what the cut line meant
as well. The second line also said *when* to run the tests. The pruned
file says that next to the right command.

Claude Code can look for some of these lines for you. `/doctor
prompt-audit` reports instructions that contradict each other or name
files and commands that don't exist, and it changes nothing until you ask
it to (@Claude Code memory). The audit finds candidates, and you still
make the call on each line.

## Watch the sessions after the cut

A pruning pass is a change to a prompt, and you test it the way you test
any prompt change: run the usual tasks and watch what the agent does. The
vendor's advice is to treat the instruction file like code, prune it
regularly, and check whether the agent's behavior really changes
(@Claude Code best practices). When a session goes wrong after the cut,
the cut line that would have stopped it comes back, and only that line.

<Pitfall title="Pointing at the rule every task needs">
A team prunes its file and moves the branch rules into `docs/git.md`,
behind the line "for branch naming, read `docs/git.md`". A week later the
agent commits a fix straight to `main`. The task was a small fix, nothing
about it mentioned branch naming, and the agent didn't open the file. Keep
a rule that applies to nearly every task in the instruction file itself.
Pointing is for detail that only some tasks need.
</Pitfall>

<Recap>
1. Every line in an instruction file is in context for every task, and a
   long file gets followed less well than a short one (@Claude Code memory).
2. Load what nearly every task needs, and point at the rest with one line
   that says when to read the file and where it is.
3. An `@path` import expands the file into the context at start-up, so it
   makes the file tidier without making it cheaper (@Claude Code memory).
4. Prune by asking of each line whether removing it would cause a mistake.
   Cut rules the agent follows anyway, facts the code states, problems
   that have gone away, and one of every pair of lines that contradict
   each other (@Claude Code best practices).
5. After a cut, run the usual tasks and add back only the line whose
   absence caused a mistake.
</Recap>

<Habit id="delete-one-when-you-add-one">
The next time you add a line to an instruction file, read the rest of the
file and delete one line that no longer prevents a mistake.
</Habit>
