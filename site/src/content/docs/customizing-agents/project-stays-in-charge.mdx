A colleague installs a skill called `ship-branch` in your project. It
commits the finished work and then pushes the branch. Your project has a
rule that agents never push: a person reviews each branch and pushes it.
In this lesson we keep that rule in charge. We take the conflict out of
our copy of the skill and add a hook that refuses the push with a
reason. Then we check that the agent takes another route after the
refusal.

The skill is invented for the course, and so is the small project it
runs in. Both are in the course repository at
`site/examples/customizing-agents/project-stays-in-charge/`, next to the
hook. The events, the JSON fields and the rule syntax are Claude Code's,
checked against the vendor's documentation on the date at the end of the
lesson (@Claude Code hooks) (@Claude Code permissions).

## When a skill and the project disagree

Here is the skill. It asks for the one thing the project's `CLAUDE.md`
forbids.

```markdown
---
name: ship-branch
description: Commit the finished work and publish the branch. Use when the user says the work is done or asks to ship it.
license: Apache-2.0
allowed-tools: Bash(git add *) Bash(git commit *) Bash(git push *)
---

# Ship the branch

1. Run `git status` and check that only the files of this task changed.
2. Stage those files and commit them with a short message in the imperative.
3. Push the branch with `git push -u origin HEAD`, so the work is never only
   on this machine.
4. Report the branch name and the commit.
```

Step 3 works against the project. It is an instruction, and the
project's `CLAUDE.md` gives the opposite one. Given two instructions
that disagree, Claude may act on either of them (@Claude Code memory). A
third line that says "follow the project, not the skill" only adds one
more instruction to weigh. The fix is to remove the conflict, and the
place to remove it is your copy of the skill. The project's rule stays
as it is.

The `allowed-tools` line also works against the project. The tools it
lists are pre-approved for the turn in which the skill starts, so Claude
runs them with no prompt. The skill's author has pre-approved `git push`
in your project (@Claude Code skills). Deny and ask rules still
override that grant (@Claude Code skills). Exit code 2 from a PreToolUse
hook ends the call before Claude Code looks at any permission rule, and
a matching allow rule then has no effect (@Claude Code permissions). A
deny decision in the hook's JSON output prevents the call too
(@Claude Code hooks). So the project's hooks and permission rules
decide, and the skill's front matter doesn't widen them.

For `ship-branch`, delete step 3 and `Bash(git push *)` from your copy,
and write down the version you copied, as
[Adopting a published skill set](/customizing-agents/adopting-a-skill-set/#take-two-skills-at-a-time)
did for two skills. The next update of the skill may bring the step
back, and the agent may still try a push on its own. The project needs a
control that holds whatever the skill says, and the rest of this lesson
builds one.

## A refusal the agent can act on

A refusal does more than stop one action. When a hook or a person blocks
an action and says why, the reason goes back to the model, and the agent
plans its next step with it. We call this **steering by rejection**. The
reason is the only part of the hook the agent sees at that moment, so it
should say what the rule is and which way is open. Here is what Claude
gets back from each kind of refusal in Claude Code.

- A PreToolUse hook can print a JSON decision of `deny` with a
  `permissionDecisionReason`. Claude Code prevents the call and shows
  Claude the reason (@Claude Code hooks).
- A hook that exits with 2 blocks the same way, and its text on standard
  error becomes the reason (@Claude Code hooks).
- When you answer No to a permission prompt, you can press Tab and type a
  comment. The comment reaches Claude as the reason for your refusal,
  and the session continues. Without a comment, a No in the main
  conversation ends Claude's turn (@Claude Code permissions).
- A deny rule in `permissions.deny`, such as `Bash(git push *)`, blocks
  every call that matches. A rule is a tool name and a pattern, so it
  has no place for a reason of yours (@Claude Code permissions).

[Writing a hook that blocks a mistake](/customizing-agents/first-hook/)
used the exit code and standard error. This hook uses the JSON form. It
exits with 0 and prints a `hookSpecificOutput` object with the event
name, the decision and the reason, the fields the hooks reference gives
for PreToolUse (@Claude Code hooks). Here is the core of it. The
complete file is
`site/examples/customizing-agents/project-stays-in-charge/no_push_guard.py`.

```python
REASON = (
    "This project doesn't let agents run git push. A person reviews each branch "
    "and pushes it. Leave your commits on the current branch, don't look for "
    "another way to push, and tell the user which branch is ready."
)


def main() -> int:
    try:
        call = json.load(sys.stdin)
        command = call["tool_input"]["command"]
        if not isinstance(command, str):
            raise TypeError("command must be a string")
    except (ValueError, KeyError, TypeError):
        print(
            "Blocked: the no-push hook couldn't read the tool call it was given.\n"
            "Check the hook's entry in .claude/settings.local.json.",
            file=sys.stderr,
        )
        return 2
    try:
        denied = pushes(command)
    except Exception as error:
        # A crash has to block the call, and exit code 1 doesn't block.
        print(f"Blocked: the no-push hook failed on this command: {error!r}", file=sys.stderr)
        return 2
    if not denied:
        return 0
    decision = {
        "hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "deny",
            "permissionDecisionReason": REASON,
        }
    }
    print(json.dumps(decision, indent=2))
    return 0
```

The reason names the rule, says who does the push instead, and gives the
agent its next step. It also asks the agent not to look for another way,
for a reason the next section shows. `pushes` splits the command into
words the way a shell does, which removes the quotes, and into
subcommands at shell operators such as `;`, `&&`, `|` and `&`. It joins
a line that ends in an unescaped backslash to the next one, as the shell
does. In each subcommand it skips leading `NAME=value` assignments and
words such as `env` and `nohup` that start the next word as a program,
with their options. It checks that the program is `git` by any path,
skips git's own options such as `-C .`, and returns true when git's
command is `push`. The shell expands a word such as `{push,}` or `$CMD`
before it runs the command. When the program or git's command is such a
word, the hook can't know the result, so it returns true if the rest of
the subcommand contains `push`. When the input isn't a tool call it can
read, the hook exits with 2 and writes why to standard error. A broken
hook then blocks the call.

The fixture `deny.py` pipes the hook the call that the skill's step 3
would make, the same way the exercise does by hand.

## What a bare refusal leaves open

A refusal without a reason still blocks the one call. What it doesn't do
is tell the agent what to do next, and the next step may be the same
action in another form. A Bash rule compares a pattern with the command
as Claude wrote it. The permissions page lists forms that a deny rule
for `Bash(git push *)` doesn't stop, such as
`git -C . push origin main`,
`git -c push.default=current push origin main` and
`git 'push' origin main`. By the page's own account, such a rule covers
the way Claude usually writes the command, and it doesn't guard the
program itself (@Claude Code permissions).

The vendor pages don't say what Claude does after a refusal that gives
no reason. What follows is our inference from the documented limits of
Bash rules. An agent that is still trying to finish the task, and that
doesn't know the rule, may try a second spelling of the same command. If
that spelling is one the rule doesn't match, the rule doesn't stop it,
and only the permission prompt stands between that push and the remote.
A reason that names the open route gives it a better move than the
second spelling. The exercise lets you watch both cases.

A hook is code, so it can catch more spellings than a pattern can. The
fixture `spellings.py` holds eleven commands against the same hook: nine
spellings of a push, a push through `sh -c`, and a `git log` that only
mentions the word. The wrapped command takes two lines of the output.

The three forms from the vendor's table are refused, and so are git by
its full path, an empty `-C` directory (which git reads as the current
one), a line wrapped with a backslash, `env` in front of git, and a word
that the shell expands to `push`. The push through `sh -c` gets through:
the hook sees `sh`, and the push is inside a quoted string that it
doesn't read. The hook also misses a push inside backticks, as in
``echo `git push` ``, or inside `$(...)`. It misses a push word held in
a variable, as in `X=push; git $X`, and a script such as `./publish.sh`
that pushes. So the hook makes the refusal and its reason reach the
agent for the spellings it reads, and we expect the reason to make a
search for another spelling less likely. Neither the rule nor the hook
is a boundary. For a limit that doesn't depend on the command text, the
permissions page points to the sandbox (@Claude Code permissions). For a
push in particular, the remote can refuse it, whatever ran the command.

<Habit id="refuse-with-a-reason">
The next time you deny an agent's action, at a prompt or in a hook, say
in one sentence what the rule is and what the agent should do instead.
</Habit>
