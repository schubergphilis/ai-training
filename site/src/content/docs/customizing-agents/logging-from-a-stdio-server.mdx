In this lesson one debug line breaks a tool server, and we find out why
the client can't read the server's reply. The fix changes where the line
goes. Then we read the log of the real file-system server while an agent
calls it.

The previous lesson connected the reference file-system server of the
Model Context Protocol (MCP) project, and showed a stand-in that speaks
the same stdio transport. Here we use that stand-in again. A quick way
to debug a server you write is a `print`, and on this transport a
`print` to standard output is a bug.

## What a debug line does to the stream

On the stdio transport the client starts the server as a child process.
The server reads requests from its standard input and writes its
messages to its standard output, one message per line in JSON-RPC, the
JSON format for Remote Procedure Calls (RPC) that MCP uses. The
specification allows nothing else on standard output. A server that wants
to log writes to standard error instead, and the client may show that
stream, pass it on or drop it. The client also shouldn't take output on
standard error as a sign that something failed (@MCP specification).
That rule is stdio logging, and the fixture below shows what happens
without it.

The fixture directory for this lesson,
`site/examples/customizing-agents/logging-from-a-stdio-server/`, holds
`server.py`. It answers each request with the stand-in's own code from
`../mcp-first-server/stand_in.py`, so it has the same three read-only
tools and the same scope. Before each answer it calls `log`, which prints
the method and the tool name:

```python
def log(message):
    print(message)
```

`check.py` plays the client. It starts a server and sends one
`tools/call` for `list_directory` on the handbook directory. Then it
reads one line from the server's standard output. It prints that line,
cut at 40 characters, and whether the line parsed as JSON. Last it prints
what the server wrote to standard error. `call_server.py` runs it against
`server.py`.

The server worked. It got the request, ran the tool and wrote a correct

work, and all the client got was a line it can't read.

## Move the log to standard error

The fix is one argument. `server_fixed.py` is `server.py` with the `log`
function changed to write to standard error:

```python
def log(message):
    print(message, file=sys.stderr)
```

`call_fixed_server.py` sends the same call to `server_fixed.py`.

<Predict id="call-the-fixed-server" title="Call the fixed server"
  answer={`stdout line: {"jsonrpc": "2.0", "id": 1, "result":...
  parsed: yes, isError: False
  stderr: debug: tools/call list_directory`} run="customizing-agents/logging-from-a-stdio-server/call_fixed_server.py">
Run `call_fixed_server.py` in the fixture directory, and compare with the
output below.

```sh
python3 call_fixed_server.py
```

</Predict>

Now the first line on standard output is the reply, and the debug line
is still there, on standard error. You kept the information and the
client gets a clean stream.

MCP also has a logging feature inside the protocol, a `notifications/message`
the server sends to the client. Revision 2026-07-28 deprecates it, and
its registry of deprecated features tells a stdio server to log to
standard error instead (@MCP deprecated features). So standard error is
the one place for a stdio server's log, whatever your client does with it.

## Read the log while the agent calls it

A client may ignore the server's standard error (@MCP specification), so
to read the log with any agent, send it to a file yourself. Start the
server through `sh -c` with `2>>` and a file name, and `sh` appends
everything the server writes to standard error to that file. Standard
output stays connected to the agent.

The reference file-system server writes its own messages to standard
error. Its source prints a line when it starts on stdio, and a line when
it replaces its allowed directories with the roots the client sent
(@MCP filesystem server). It doesn't log each tool call. This is
its log from a run on October 7, 2026, with version 2026.8.31 and a
small test client that sent one root:

```text
Secure MCP Filesystem Server running on stdio
Updated allowed directories from MCP roots: 1 valid directories
```

The previous lesson showed that Claude Code sends the directory you
started it in as a root (@Claude Code mcp), so under Claude Code the
second line tells you the server took its scope from that directory.
On that run `npx` also wrote two `npm notice` lines of its own to
standard error, so your file may hold lines like those too.

<Pitfall title="A library that prints">
A developer adds a library to their stdio server, and the library prints
a one-line banner to standard output the first time it is used. In their
own test they start the server in a terminal, type a request, and read
the reply by eye, so the banner looks like harmless extra text. In the
agent the first tool call fails with a parse error that names neither
the banner nor the library. The rule: on a stdio server, only the code
that writes protocol messages writes to standard output. Send every other
line to standard error, and test the server with a client that parses
each line, as `check.py` does.
</Pitfall>


yourself: if the server had printed those lines to standard output
instead, what would the agent have shown you?
</Exercise>

<Recap>
1. On the stdio transport, standard output carries one JSON-RPC message
   per line and nothing else. A server logs to standard error, which the
   client may show, keep or drop, and which isn't a sign of failure
   (@MCP specification).
2. A `print` writes to standard output by default, so one debug line
   arrives where the client expects a reply and the client can't parse
   it. The server did its work, and the client sees a broken stream.
3. The fix is to write the line to standard error, which keeps the
   information. MCP revision 2026-07-28 deprecates the in-protocol
   logging feature and points stdio servers to standard error
   (@MCP deprecated features).
4. To read a server's log with any agent, start it through `sh -c` and
   append its standard error to a file, then read the file in a second
   terminal.
</Recap>
