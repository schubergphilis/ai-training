In this lesson we read a week of traces from an agent that staff use
every day and label each run good or bad. The failures of a kind that
the golden set has no case for become new cases. The previous lesson put a gate
in front of every change, and the gate ran 21 questions. Staff ask
hundreds a week, and some of their questions are unlike anything in the
set. **Trace-driven evaluation** brings those questions into the set. The agent logs every
run, and people read a sample of the traces. Each bad run of a new kind
becomes a case that the next change must pass.

The agent is the handbook assistant of
[Gating a deploy on the evaluation](/building-agents/eval-gated-deploys/),
and the rollout of that lesson is finished. The shorter fixed prompt is
live for the whole office, and it is `prompts/current.txt` in this
lesson's copy. The gate, the golden set and the stricter candidate prompt are the
files of that lesson. The files are in
`site/examples/building-agents/evals-from-traces/`. Copy the
`evals-from-traces` folder, and run each step below from inside the copy,
as `python3 traces.py <step>` or `python3 gate.py <prompt>`. No
application programming interface (API) key is needed.

The traces in this lesson are invented, and so are the people and their
employee numbers. Real traces come from the trace store that a production
agent writes to, and they hold what real people typed, which can be
personal data.

## Log every run, and read a sample

Before people or a model can judge what an agent did, its runs have to be
logged (@Husain 2024). The assistant writes one trace per run. Its records
use the fields of
[Recording and grading the path the agent took](/building-agents/traces-and-trajectories/).
A tool record holds the search, and a model record holds the answer. The
records here leave out the token counts, the latency and the cost, which
this lesson doesn't use, and they add `user`, the employee number of the
person who asked.

How much to read changes over time. Husain reads as much as he can when
a product is new, and reads a smaller sample as it matures, but he never
stops reading (@Husain 2024). This team picks 20 runs at random from each
week and reads them on Friday. He also says that reading must take as
little effort as possible, and he often builds his own viewer that puts
everything a reader needs on one screen (@Husain 2024). The `week`
step is this team's viewer. It prints each run of the sample with its
question and the answer the person got.

## Label each run good or bad

A trace has no expected answer. Nobody wrote one, because nobody knew the
question would come. The reader decides whether the run was good, here by
checking the answer against the handbook pages in `docs/`. Husain starts
with a label of good or bad for each trace, because finer scores are
harder to manage than two labels (@Husain 2024).

Sixteen of the twenty runs are good. Three of them answer "not found",
and that's right. The handbook says nothing about taxis or coffee, and
nothing about a gym. Runs w1-04, w1-08, w1-11 and w1-13 are bad. For each one, write down the first step that
went wrong, the way
[Reading failures one by one](/building-agents/error-analysis/)
did:

| Run   | What went wrong                                                        |
| ----- | ---------------------------------------------------------------------- |
| w1-04 | no rule for sick leave, and the agent quoted the annual leave rule     |
| w1-08 | the handbook calls it "annual leave", and the search got expenses      |
| w1-11 | no rule for parental leave, and the agent quoted the annual leave rule |
| w1-13 | the answer needs a second lookup, the data team page                   |

Runs w1-04 and w1-11 are the worst of the four. A person who asked about
sick leave was told a rule that the handbook doesn't have. The question
shares two words with the annual leave sentence, "days" and "leave", and
two shared words are enough for the agent to answer.

## Which failures does the set already have?

In [Reading failures one by one](/building-agents/error-analysis/) each
of the ten failures added an item. A weekly sample brings the same kinds
back week after week. So here a bad run of a kind that the set already
has adds to the count of that kind, and a bad run of a new kind becomes
a case. For each bad run, look in `golden-set.csv` for an item that
would fail on the same mistake, at the same step.

- w1-08 has the kind of a01, "How much holiday can I take?". In both runs
  the search doesn't return the page with the answer, because the handbook
  doesn't use the user's word. For w1-08 it returns the expenses page, and
  for a01 it doesn't find a page. The set accepts "not found" from a01, and the
  `helpful` metric already counts it as a failure.
- w1-13 has the kind of r08. The search returns the laptop page, and the
  answer needs a second lookup, the team page. r08 fails on every prompt
  today, and the routine threshold of the previous lesson allows it.
- w1-04 and w1-11 have no item of their kind. The refuse items x01
  to x06 all get "not found" today, because none of them shares two words
  with a sentence in the handbook. So the gate passed while staff got a
  made-up leave rule.

A failure of a kind that the set already has tells you how often that
kind happens, and the count helps you choose what to fix first. A new
kind tells you what the set is missing. This week has one new kind,
with two runs.

<Pitfall title="Pasting the trace into the set as it is">

A team adds a case from a trace in a hurry, with the question as the
person typed it: a name, a diagnosis and an employee number. Many people
read the golden set. A contractor reads it, and the file goes into a
copy for a vendor. Six months later someone notices and deletes the line,
and every earlier commit still holds it. Take out the details that point
at a person before the case is written. Then check that the stripped
question still fails.

</Pitfall>
