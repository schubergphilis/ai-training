In this lesson we run three fixed arrangements of model calls for a small
shop that answers customer emails. In each one the code decides which call
comes next, and the model only writes the text of each call. After that we
look at a kind of task that fixed code can't hold, and that needs an agent
that chooses its own steps.

In [Stopping the loop on purpose](/building-agents/stopping-the-loop/) the
model chose every tool call, and the harness rules decided when the run
ended. Here the order of the calls is written in the program before the
first email arrives. The model calls are fake: functions written by hand
that read a prompt name and some text and return text. Every run prints
the same result. The complete program is
`site/examples/building-agents/workflows-before-agents/workflows.py` in
the repository. Copy the `workflows-before-agents` folder, and run each
step below inside your copy as `python3 workflows.py <step>`. No
application programming interface (API) key is needed.

## Who decides the next step

Anthropic's engineering article on building agents sorts systems that use
models into two kinds (@Anthropic effective agents). In a workflow, the
path through the model calls and the tools is set in code that the
developers wrote. In an agent, the model directs the process itself and
picks the tools it uses as it goes. The article advises starting with the
simplest thing that works. Often that's one model call, prepared well,
with retrieved text and a few examples in the prompt. Add steps only when
the simpler version doesn't do the job well enough, because each step
adds time and cost (@Anthropic effective agents).

Between one call and an agent are the workflow patterns: fixed
arrangements of model calls, inside one task, where code controls the
order. This lesson runs a chain, a route, and parallel calls. A fourth, a
draft-and-critique loop, gets
[its own lesson later in this part](/building-agents/reflection/). When
the parts of the task are whole agents that hand work to each other, the
design is a multi-agent system. The lesson
[Orchestration in code or by a model](/building-agents/orchestrating-agents/)
opens the part of the course that covers it.

## A chain with a gate

A chain runs model calls one after another, and each call works on what
the call before it returned. Code can check the output between two calls
and stop the chain when the check fails (@Anthropic effective agents). The
article recommends a chain for a task that breaks into the same steps
every time. Each call then has a smaller job and is more likely to get it
right, and the price is the time of the extra calls
(@Anthropic effective agents).

The shop's chain has two calls. `extract` reads the email and returns the
order number and what the customer wants. The `gate` is plain code. It
looks the order up. When it finds the order, `write` writes the reply.
Any other email goes to a person.

```python
def chain(email_id: str) -> None:
    calls.clear()
    print(f"chain, email {email_id}")
    extracted = model("extract", EMAILS[email_id])
    print(f"  call 1 extract: {extracted}")
    facts = gate(extracted)
    if not facts:
        print("  gate: no known order, the email goes to a person")
    else:
        print(f"  gate: order {facts.split()[0]} found")
        print(f"  call 2 write: {model('write', facts)}")
    print(f"  model calls: {len(calls)}")
```

Email `a1` names order 1042. Email `a2` asks for a replacement toaster and
doesn't name an order.

## A route to a prompt per class

A route has one call that sorts the input into a class, and code then sends
the input to the prompt or the process for that class. The article
recommends it when the inputs come in distinct kinds, and each kind gets
better answers from its own prompt. With one prompt for every kind, a
change that helps one kind of input can make the answers to another kind
worse (@Anthropic effective agents). A route can also
send easy inputs to a small and cheap model, and hard ones to a stronger
model (@Anthropic effective agents).

The shop's `classify` call returns `refund`, `repair`, `question` or
`other`. Each of the first three has its own prompt. The refund prompt
knows the 30-day limit, and `other` has no prompt, so code sends it to a
person.

```python
for email_id in ["b1", "b2", "b3", "b4"]:
    label = model("classify", EMAILS[email_id])
    if label in ROUTES:
        answer = model(ROUTES[label], EMAILS[email_id])
    else:
        answer = "(no prompt for this class, the email goes to a person)"
    print(f"  {email_id} {label:<8} {answer}")
```

## Parallel calls

Parallel calls come in two forms (@Anthropic effective agents). Sectioning
splits the work into independent parts and runs them at once. For example,
one call writes the reply while another checks the email for something a
person must handle. Voting asks one question several times and combines
the answers. A judgment that one call can get wrong becomes more
reliable that way. The article recommends parallel calls for parts that
can run side by side to save time, or for a judgment that needs more than
one attempt to trust (@Anthropic effective agents).

In the shop, email `c1` mentions a card number, and the `screen` call runs
next to the `reply` call. Email `c2` doesn't say whether the customer
wants a refund or a replacement. Three `vote` calls answer that question,
and the shop acts on the answer that most of them give. The fixture counts
2 seconds per model call. The seconds are an assumption written by hand,
to compare one way of running the calls with the other.

## When the task needs an agent

Each pattern so far has a path that you can draw before the first email
arrives, branches included. The route picks one of four paths, and the
chain either stops at the gate or goes on. Each of those paths is in the
code. An agent fits a task where you can't draw the paths. Think of a
search for the cause of a fault: each finding opens new places to look,
and the count of steps is unknown at the start. The article keeps agents
for tasks like that, where nobody knows the number of steps or the path
before the work begins (@Anthropic effective agents). An agent is the loop
from the earlier lessons: the model calls tools, reads what they return,
and decides the next step until it is done or a stop rule ends the run.

That freedom has a price. An agent costs more to run, and a wrong early
step can make the steps after it go wrong too. The article advises
testing it a lot in an environment where its mistakes do no harm, with
limits on what it can do (@Anthropic effective agents). So the question
for a new task is whether you can list its possible steps today and draw
the paths between them. If you can, write them as code and call the model
inside each step. If nobody can list them before the task starts, you
need an agent, and its stop rules from the earlier lesson.

<Pitfall title="A chain without a gate">
A team chains two calls: one reads the customer's email and pulls out the
order number, and the next writes the reply from it. The code passes the
first output to the second call without a check, so on an email without
an order number the first call returns `none` and the second writes a
confident reply about a replacement for an order that doesn't exist. Put
a check in code between the calls, and send what fails the check to a
person, the way the shop's `gate` did with email `a2`.
</Pitfall>

<Recap>

1. In a workflow, code decides the path of the model calls. In an agent,
   the model decides its own steps and tools (@Anthropic effective agents).
2. Start with the simplest version that works, often one model call, and
   add calls only when it doesn't do the job well enough
   (@Anthropic effective agents).
3. A chain runs calls in a fixed order, each on the output of the one
   before, and code between them can stop it. A route sorts the input and
   sends it to a prompt per class. Parallel calls split a task into
   independent sections, or ask one question more than once and act on
   the answer most calls give (@Anthropic effective agents).
4. A task needs an agent when nobody can list its possible steps or draw
   its paths before it starts. A branch that code can write down, as in
   a route, is still a workflow. The agent then
   costs more and needs stop rules and testing where its mistakes do no
   harm (@Anthropic effective agents).

</Recap>

<Habit id="check-between-calls">
The next time you put one model call after another, write down what code checks the first call's output before the second call uses it.
</Habit>
